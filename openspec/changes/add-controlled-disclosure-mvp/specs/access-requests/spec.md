# Delta for access-requests

## ADDED Requirements

### Requirement: Отправка запроса на расширенный доступ
Анонимный посетитель SHALL иметь возможность отправить запрос на расширенный доступ к одной опубликованной карточке
через `POST /api/v1/cards/{id}/access-requests` с полями: `email` (RFC 5322, ≤ 254), `display_name` (≤ 60, буквы/цифры/пробел/дефис),
`purpose` (≤ 1000), `consent` (true — согласие на обработку синтетических данных на срок хранения).
Иные поля MUST отвергаться (422).

#### Scenario: Успешная отправка
- **GIVEN** карточка опубликована
- **WHEN** посетитель отправляет валидную форму с CSRF-токеном
- **THEN** создаётся `access_request` в статусе `pending`, ответ 202 с телом `{"status":"received"}`, событие `request.created` в аудите

#### Scenario: Mass assignment (TC-API-02)
- **WHEN** тело запроса содержит `status: "approved"` или `card_id` другой карточки
- **THEN** ответ 422, запрос не создаётся

#### Scenario: XSS в полях формы (TC-API-03)
- **WHEN** `purpose` содержит `<script>alert(1)</script>`
- **THEN** значение сохраняется как текст и при отображении reviewer экранируется (скрипт не исполняется)

### Requirement: Единообразный ответ без раскрытия состояния
Ответ на отправку запроса MUST быть одинаковым (202, одно и то же тело) независимо от того, есть ли уже запрос с этим e-mail,
опубликована ли карточка (для неопубликованной — запрос молча не создаётся) и т.д. Это исключает перебор e-mail и карточек.

#### Scenario: Повторный запрос с тем же e-mail
- **GIVEN** для пары (e-mail, карточка) уже есть `pending`-запрос
- **WHEN** отправлен ещё один
- **THEN** ответ идентичен первому, новый запрос не создаётся, в аудите `request.duplicate`

### Requirement: Минимизация данных запроса
Система SHALL хранить e-mail только в зашифрованном виде (`email_enc`, Fernet) и HMAC-хеш для поиска дублей и rate limit.
E-mail MUST NOT записываться в логи и аудит; в аудите используется псевдоним запроса.

#### Scenario: E-mail не в открытом виде (TC-LEAK-05)
- **WHEN** выполнен дамп таблицы `access_requests` и логов контейнеров
- **THEN** строка e-mail не встречается в открытом виде

### Requirement: Защита от флуда запросов
Система MUST ограничивать отправку: ≤ 5 запросов в час с одного IP и ≤ 3 в сутки на один e-mail (по HMAC).
Форма SHALL содержать honeypot-поле; заполненный honeypot → ответ 202 без создания запроса.

#### Scenario: Превышение лимита (TC-RL-01)
- **WHEN** с одного IP отправлено 6 запросов за час
- **THEN** 6-й получает 429, в аудите `request.rate_limited`

### Requirement: Уведомление requester
После решения reviewer система SHALL отправить requester письмо (через Mailpit): при одобрении — одноразовую ссылку,
при отказе — нейтральный текст без причин. Письмо MUST NOT содержать confidential-содержимое карточки.

#### Scenario: Письмо об отказе
- **WHEN** reviewer отклонил запрос
- **THEN** requester получает письмо «Запрос не может быть удовлетворён» без `reason_code` и внутреннего комментария
