# Delta for staff-auth-rbac

## ADDED Requirements

### Requirement: Вход сотрудников с MFA
Reviewer и admin SHALL входить по e-mail + пароль (argon2id через `argon2-cffi`) и обязательный TOTP (`pyotp`, окно ±1 шаг).
Регистрация через UI MUST NOT существовать; тестовые аккаунты создаются CLI-командой `manage.py create-staff`.
Сообщение об ошибке входа MUST быть единым («Неверные данные для входа») для любого неверного фактора.

#### Scenario: Успешный вход
- **WHEN** сотрудник вводит верные пароль и TOTP
- **THEN** создаётся новая сессия `__Host-sid` (новый ID, старый инвалидирован), событие `auth.login_success`

#### Scenario: Неверный TOTP (TC-AUTH-02)
- **WHEN** пароль верный, TOTP неверный
- **THEN** ответ 401 с общим сообщением, событие `auth.login_failed` (без указания, какой фактор неверен)

#### Scenario: Повтор использованного TOTP-кода
- **WHEN** тот же TOTP-код используется повторно в пределах его окна
- **THEN** вход отклоняется

### Requirement: Защита от перебора паролей
После 5 неудачных попыток для аккаунта система MUST блокировать вход на 15 минут; rate limit 10 попыток/мин на IP.
Время ответа для существующего и несуществующего e-mail SHALL быть сопоставимым (dummy-хеширование).

#### Scenario: Блокировка (TC-AUTH-03)
- **WHEN** выполнено 6 неудачных попыток
- **THEN** 6-я и последующие в течение 15 мин отклоняются даже с верными данными, событие `auth.locked`

### Requirement: Staff-сессии
Staff-сессия MUST храниться на сервере (Redis), ID ≥ 128 бит, idle 30 мин, absolute 8 ч.
Logout MUST удалять сессию на сервере. Деактивация аккаунта admin'ом MUST немедленно завершать его сессии.

#### Scenario: Сессия после logout (TC-AUTH-04)
- **WHEN** после logout повторно использована старая cookie
- **THEN** ответ 401

#### Scenario: Фиксация сессии (TC-AUTH-05)
- **WHEN** до входа установлена cookie `__Host-sid` с заданным атакующим значением
- **THEN** после входа выдаётся новый ID, исходное значение недействительно

### Requirement: RBAC с запретом по умолчанию
Каждый маршрут API SHALL явно объявлять допустимые роли через FastAPI-dependency; маршрут без объявления MUST
отклоняться тестом CI (проверка всех маршрутов приложения). Роль берётся только из серверной сессии, не из запроса/JWT/cookie.

#### Scenario: Reviewer публикует карточку (TC-RBAC-02)
- **WHEN** reviewer вызывает `POST /api/v1/staff/cards`
- **THEN** ответ 403, событие `authz.denied`

#### Scenario: Анонимный вызов staff API (TC-RBAC-05)
- **WHEN** запрос без сессии к `/api/v1/staff/requests`
- **THEN** ответ 401

#### Scenario: Тест покрытия маршрутов
- **WHEN** запускается тест, обходящий `app.routes`
- **THEN** каждый маршрут, кроме allowlist публичных, имеет dependency авторизации, иначе тест падает

### Requirement: Управление тестовыми аккаунтами
Admin SHALL иметь возможность деактивировать/активировать reviewer-аккаунты и сбрасывать TOTP (с выдачей нового секрета через CLI).
Admin MUST NOT иметь возможности деактивировать себя или изменить свою роль.

#### Scenario: Деактивация reviewer
- **WHEN** admin деактивирует reviewer
- **THEN** все сессии reviewer удалены, событие `staff.deactivated`
