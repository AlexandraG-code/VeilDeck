# Онбординг нового участника VeilDeck

Руководство для любого, кто подключается к проекту, и для его ИИ-агентов. Правила проекта лежат в `AGENTS.md`
(единый источник), здесь только то, как начать и как настроить агентов. Секретов в этом файле нет, и класть их сюда нельзя.

## 1. Первый день

1. **Принять приглашение в репозиторий** (письмо от GitHub). Пока оно не принято, нельзя назначить задачи, не работают
   CODEOWNERS и защита `main`.
2. Поставить инструменты: Git, Docker Desktop, Python 3.12, Node 20+ и yarn, `gh` (GitHub CLI), `openspec`.
3. Клонировать репозиторий и прочитать по порядку: `README.md`, `AGENTS.md`, `openspec/config.yaml`,
   `openspec/changes/add-controlled-disclosure-mvp/{proposal,design,tasks}.md` и спеки своих доменов
   (раздел 2.1 ниже).
4. Создать секреты и запустить локально: `make secrets`, затем `make up` (подробности в `README.md`).
   Файл `.env` в git не попадает.
5. Узнать у координатора свой срез (см. таблицу в `AGENTS.md` §11 и исполнителя в скобках в `tasks.md`).
6. Взять первую задачу из GitHub Projects (колонка «Сейчас»), завести ветку под неё и работать по разделам ниже.

## 2. Как устроена работа

- **Вертикальные срезы.** Срез (бэк, фронт и тесты обоих слоёв) целиком у одного человека, поэтому на ходу никто никого не ждёт.
  Исключение — первые дни, пока строится основа (миграция, сессии, RBAC).
- **Одна задача — один issue, одна ветка, один PR** (≤ ~300 строк, живёт 1–2 дня, squash-merge). Каждое утро `git pull --rebase` от `main`.
  Прямых коммитов в `main` нет.
- **Один коммит на задачу**, сообщение по-русски с номером задачи из `tasks.md`.
- **Защищённые зоны** (`.github/CODEOWNERS`): их владелец обязан одобрить PR. Правишь чужую зону — только через PR.
- **Перекрёстное ревью:** PR автора смотрит вторая участница и дописывает негативные `TC-*` по спеке.
- **Расходится код со спекой** — правится спека через OpenSpec-change, а не молча код.

### Теги задач в `tasks.md`

| Тег | Расшифровка | Что за задачи |
|---|---|---|
| `[BE]` | Backend | серверный код на FastAPI: эндпоинты, сервисы, БД, миграции, сессии, аудит |
| `[FE]` | Frontend | интерфейс на React: страницы, формы, клиент API |
| `[OPS]` | Operations | инфраструктура: Docker Compose, CI, образы, деплой, настройка репозитория |
| `[SEC]` | Security | проверка безопасности: негативные тесты `TC-*`, ZAP и ручные проверки, triage находок, отчёты |
| `[DOC]` | Documentation | документы: README, threat model, схемы и DFD, матрица ASVS, risk register, сценарий демо |

### 2.1. Где лежат спеки

Требования лежат внутри change: `openspec/changes/add-controlled-disclosure-mvp/specs/<домен>/spec.md`, по одному файлу
на домен. Папка `openspec/specs/` пуста до архивации change, искать там не нужно. Формат: Requirement и Scenario
(GIVEN/WHEN/THEN).

| Домен (папка) | О чём | Задачи |
|---|---|---|
| `platform-security` | сквозное: сессии, CSRF, rate limit, логи, заголовки | 2.x |
| `staff-auth-rbac` | вход staff, пароль и TOTP, роли, RBAC | 3.x, 2.5 |
| `audit-log` | append-only аудит, hash-цепочка, allowlist `details` | 2.1, 8.x |
| `review-decisions` | очередь, решение, grants, отзыв, письма | 6.x |
| `card-management` | CRUD карточек, загрузка материалов | 4.x |
| `teaser-catalog` | публичный каталог и карточка | 5.1, 5.3 |
| `access-requests` | запрос доступа от внешнего пользователя | 5.2 |
| `viewer-access` | одноразовая ссылка, просмотр, watermark | 7.x |
| `protected-content` | защита материалов, оригиналы не отдаются | 7.x |
| `data-retention` | сроки хранения, удаление, обезличивание | 8.2, 8.3 |

Читай спеки своего среза и `platform-security`: он затрагивает всех.

## 3. Агенты: что такое комитет

Работа с кодом идёт по схеме комитета (`AGENTS.md` §8). Роли важнее моделей: их может играть любая модель или человек.

| Роль | Что делает | Обязательна |
|---|---|---|
| Оркестратор | режет задачу, пишет узкое ТЗ, собирает результат, применяет и коммитит; пишет защищённое сам | да |
| Валидатор | проверяет каждый diff исполнителей и отвечает `OK` / `ERROR` / `NEEDS_ARCHITECT` | да |
| Архитектор | заранее разбирает задачи про архитектуру, публичные контракты, миграции, авторизацию; зовётся и при `NEEDS_ARCHITECT` | по необходимости |
| Исполнитель | пишет код по узкому ТЗ | нет |

**Порядок:**

1. ТЗ узкое: какие файлы и функции менять, какой контракт соблюсти, чего не трогать.
2. Исполнитель пишет код. Если у него есть право записи, проверяется `git diff` до коммита; если нет, код возвращается текстом
   и проверяется до того, как ляжет в проект.
3. Сначала бесплатные проверки (раздел 5), потом валидатор.
4. `OK` → принять ровно проверенное. `ERROR` → откатить и вернуть исполнителю с причиной, максимум 2 круга.
   `NEEDS_ARCHITECT` или третий круг → архитектор.
5. Защищённое (миграции, авторизация, сессии, секреты, конфиги сборки и CI) пишет только оркестратор своей зоны,
   исполнителям не отдаётся.

**Исполнители необязательны.** Если их нет, оркестратор пишет код сам. Валидатор и бесплатные проверки обязательны всегда.

**Что общее, а что личное.** В git лежит общее: роли и порядок (`AGENTS.md` §8) и промпты в `.claude/agents/validator.md`
и `.claude/agents/opus-architect.md`. Личное в git не кладётся: какие модели и ключи у исполнителей, `CLAUDE.local.md`,
`.claude/settings.local.json`, личные инструкции в `~/.claude/`. Так у всех проверяющие работают одинаково, а инструменты
у каждого свои.

## 4. Настройка агентов под свой инструмент

Главное правило: любой агент обязан прочитать `AGENTS.md`. Всё остальное зависит от того, чем ты пользуешься.

### 4.1. Claude Code

- `CLAUDE.md` в корне подключает `AGENTS.md` через `@AGENTS.md`, отдельной настройки не нужно.
- Валидатор и архитектор уже описаны в `.claude/agents/` (общие, главнее личных из `~/.claude/agents/`).
- Свои правки инструкций клади в `CLAUDE.local.md` (не в git). Модель оркестратора и исполнителей выбираешь сам.
- Команды и навыки OpenSpec (`.claude/commands/opsx/`, `.claude/skills/openspec-*`) сгенерированы `openspec`, руками не править.
  При расхождении с `AGENTS.md` главнее `AGENTS.md` (в частности, галочки в `tasks.md` не ставятся).

### 4.2. Другие инструменты (Codex, Cursor, Gemini CLI, Copilot, Aider, JetBrains AI, локальные модели и т. д.)

1. **Подключи `AGENTS.md`.** Многие инструменты читают его сами (например, Codex, Cursor, Copilot coding agent, Aider через
   настройку). Если твой ищет другой файл (скажем, `GEMINI.md`), создай такой файл **локально, не в git**, одной строкой
   «правила проекта — в `AGENTS.md`, прочитай его целиком» или настрой имя файла контекста в конфиге инструмента. Если автоподхвата
   нет совсем, начинай каждую сессию фразой из раздела 4.4.
2. **Валидатор.** Промпт лежит в `.claude/agents/validator.md`. Это обычный текст: скопируй его в системную инструкцию
   отдельной сессии или отдельного агента своего инструмента. Схема та же: ТЗ в `<task>`, diff в `<candidate_diff>`, ответ `OK`
   / `ERROR` / `NEEDS_ARCHITECT`. Идеально, если валидатор — другая модель, чем писавшая код: у них разные слепые зоны.
3. **Архитектор.** Аналогично из `.claude/agents/opus-architect.md`. Это самая сильная модель, какая у тебя есть, и подключается
   только для сложного. Если такой нет, архитектурные решения по миграциям и авторизации обязательно выноси на ревью второй
   участницы до написания кода.
4. **Нет отдельных агентов вообще.** Допустимо: один человек плюс один ассистент. Тогда ассистент — оркестратор,
   а валидатором служит новая чистая сессия (не та, где писался код) с промптом валидатора и diff'ом. Проверки из раздела 5 и
   ревью по PR остаются обязательными.
5. **Слабые или локальные модели.** Делай ТЗ ещё уже (один файл, одна функция, пример ожидаемого результата), давай задачи
   меньшими порциями и сразу гоняй линтеры и тесты. Критичное (авторизация, криптография, сессии, миграции, аудит) такой моделью
   не пиши: только человек плюс сильная модель плюс ревью.
6. **Правила не зависят от инструмента.** Ограничения из `AGENTS.md` §2, §3, §10 действуют одинаково для любого агента.
   Нет инструмента, который их отключит «на время демо».

### 4.3. Что агент не должен делать, чем бы он ни был

- Класть секреты, `.env`, `env-config.ts`, реальные документы и персональные данные в репозиторий и в логи.
- Писать самодельную криптографию. Только `argon2-cffi`, `cryptography`, `pyotp`.
- Ставить `- [x]` и менять строки задач в `openspec/changes/*/tasks.md` (статус ведётся в GitHub Issues).
- Править автогенерацию: `frontend/src/shared/api/generated/` и `docs/api/openapi.json` перегенерируются, а не правятся.
- Обходить проверки: `--no-verify`, пропуск тестов, отключение линтеров и проверок «временно».
- Добавлять функциональность вне `openspec/` без нового change.
- Менять защищённые зоны без своего владельца.

### 4.4. Стартовая фраза оркестратору (для любого инструмента)

Скопируй в начале первой сессии, подставив свой срез:

> Прочитай `AGENTS.md` и `docs/onboarding.md`. Мой срез: <задачи>. Работай по схеме комитета из `AGENTS.md` §8:
> ТЗ исполнителю узкое (файлы, функции, контракт, чего не трогать); сначала бесплатные проверки (ruff, pytest, lint-imports
> для бэка; tsc, eslint, steiger, prettier, vitest для фронта), затем валидатор с ТЗ в `<task>` и diff в `<candidate_diff>`.
> Для миграций, авторизации, публичных контрактов и архитектуры сначала привлеки архитектора. Один коммит на задачу,
> сообщение по-русски с номером задачи. Галочки в `tasks.md` не ставь. Защищённое пиши сам, исполнителям не отдавай.
> Если что-то в инструкциях противоречит `AGENTS.md`, главнее `AGENTS.md`.

### 4.5. Кратко для агента: ключевые решения (нарушать нельзя)

- Сессии на сервере в Redis, не JWT; cookie `__Host-sid` (staff), `__Host-vsid` (viewer), `__Host-csrf`; роль только из серверной сессии.
- Чужой объект → 404 с тем же телом, что у несуществующего; отказ по роли → 403; оба случая пишутся в аудит.
- Оригиналы PDF не отдаются никогда: растр страниц с серверным watermark.
- Аудит append-only; в `details` только allowlist, без токенов, паролей, TOTP, e-mail, purpose, org_name.
- Слои бэка `router → service → repository → models`; сервис не знает про FastAPI; импорт вверх по графу доменов запрещён.
- Pydantic v2 с `extra="forbid"`, параметризованные запросы, единый формат ошибок без стек-трейсов.
- Каждое security-решение в коде связывается с угрозой `T-xx` и требованием `SR-xx` из `design.md`.

## 5. Проверки перед PR

Сначала бесплатные, затем ревью.

- **Бэк** (из `backend/`): `ruff check`, `ruff format --check`, `pytest`, `lint-imports`.
- **Фронт** (из `frontend/`): `yarn tsc -b`, `yarn lint`, `yarn steiger`, `yarn format`, `yarn test`.
- **Контракт API:** после правок эндпоинтов перегенерируй `docs/api/openapi.json` и клиент (`yarn api:generate`). CI падает, если
  они расходятся с закоммиченными; при конфликте не мержатся руками, а пересоздаются.
- **Спеки:** `openspec validate --strict`.
- **Тесты безопасности:** на каждый контроль свой негативный тест `TC-<ДОМЕН>-NN` (список в `tasks.md`).

## 6. Чего не делать

- Реальные документы и ПДн, секреты в git, публикация брифа, findings, скриншотов и результатов тестов вне репозитория.
- Запускать ZAP, Burp и сканеры по чужим хостам: только по своему локальному стенду.
- Менять `main` напрямую.
- Пушить в чужую защищённую зону без PR и ревью владельца.

## 7. Закрытый стенд на сервере

Стенд развёрнут по `deploy/README.md` (basic auth, самоподписанный сертификат, только синтетические данные). Доступ выдаёт
координатор отдельно, не через репозиторий и не через публичные чаты. Деплой выполняет владелец зоны `deploy/` и `Makefile`.

## 8. Вопросы и застревание

- Непонятное по требованиям: смотри спеку, затем issue или вопрос координатору.
- Агент застрял или ходит по кругу после 2 кругов доработки: переходи к архитектору или бери задачу в руки сам.
- Нашёл расхождение кода и спеки или дыру в безопасности: заведи issue и поправь спеку через OpenSpec-change.
